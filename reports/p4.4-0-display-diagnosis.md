## 3. 用户要求排查的 4 项（逐条结论）

1. **无头 Chrome 是否访问了同一端口与同一份构建产物** —— 是。两轮 `href` 均为 `http://127.0.0.1:5180/?year=2010`，资源来自源码路径（`/src/main.tsx?t=…`、`/src/data/snapshots.ts`、`/src/data/loadYear.ts?t=…`）= 同一个 dev 服务（PID 25808）。不存在「无头跑在另一份产物上」的情况。
2. **是否等待时间不足导致截图早于数据加载完成** —— 是，这是唯一成因。旧命令用 `--virtual-time-budget=25000` + Chrome 自带 `--screenshot`：虚拟时间把 25 s 预算压缩为约 1.4 s 真实时间（stderr 时间戳 173021.5 → 173022.9），而年份数据在页面寿命约 1.5 s 才到达（实测 1481→1495 ms），MapLibre 还需要 worker 瓦片化 + 再一帧 WebGL 绘制 —— 截图正好落在「背景与经纬网已画、政区瓦片未到」的首帧。改为真实等待 8 s 后，同一 URL 得到的是完整彩色地图（字节数 22,832 B → 216,275 B）。
3. **5180 / 5181 是否存在版本差异** —— 不存在。`dist/assets/*` mtime = `2026-10-05 17:14:05`，晚于最后一次源码改动（`src/components/MapView.tsx` 17:11:55、`src/styles.css` 17:11:50），即预览产物就是当前源码的构建。差异仅形态：dev 走源码模块 + `/@vite/client`；preview 走 hash 包（`index-DreZyiTk.js` + `react-BPeupeul.js` + `maplibre-xB6oindq.js` + `index-CsjicdzM.css` + `maplibre-B8-mEBLf.css`）。附带发现：在 5181 页面上我的「React fiber 找 `MapView`」探针失效（`mapViewFound=false`），原因是生产构建压缩掉了组件函数名 —— 探针局限，非页面缺陷。
4. **为什么 headless 与真实浏览器的结果不同** —— 三条叠加：(a) `--virtual-time-budget` 让计时器快进但不让真实时间流逝，页面只活了约 1.4 s；(b) `--screenshot` 在预算耗尽的瞬间取帧，不等瓦片化后的下一帧；(c) SwiftShader 软件渲染慢（4 条 `GPU stall due to ReadPixels`），把「数据到达 → 瓦片化 → 上屏」的窗口进一步拉长。真实浏览器里这段等待由用户浏览时间天然覆盖，因此总是能看到已绘制的政区。
