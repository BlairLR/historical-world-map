## 1. Executive Summary

| # | 结论 |
|---|---|
| 1 | `entityId` 的语义与实现**完全不变**：它仍然是「这个 feature 代表的历史政权（polity）是谁」，颜色仍然**只**由 `color = f(entityId)` 决定。 |
| 2 | 新增一层**关系层**，由三个独立字段组成：`sovereignId`（法理主权主体）、`authorityId`（实际控制 / 占领 / 军管 / 行政管理主体）、`relationship`（单一值枚举）。 |
| 3 | 关系层是**只读的下游投影**：`entityId` 是它的输入证据之一（可选），但**任何关系字段都不得参与 entityId 解析，也不得参与颜色分配**。方向被物理隔离（不同文件、不同 resolver、不同产物）。 |

### 2.4 基线的三个结构性问题（本阶段要解决的设计问题）

**(P1) 一个 raw key 混装多个语义角色。** `key = SUBJECTO || NAME` 使同一 key 在同年可以同时覆盖「母国自身 / 殖民地 / 占领区 / 君合国」。实测 1945 年 `united kingdom` key 下有 25 个 feature，其中 **只有 1 个是英国本土**（`id=4`），其余 24 个是 Jamaica (UK)、Sierra Leone、Tanzania, United Republic of、Northern Rhodesia、Nyasaland、Rhodesia、Botswana、Swaziland、Lesotho、Gold Coast、Nigeria、Southern Cameroon、Egypt、Sudan、**Eritrea**、Gambia, The、Kenya、Uganda、Somalia、British Somaliland、Cyraneica (UK Lybia)、Tripolitana (UK Lybia)、Hong Kong、Germany (UK)。它们当前**全部**是 `UK-UNITED-KINGDOM`，即**同一个 polity、同一种颜色**。

**(P2) raw key 被当成 polity identity。** `SUBJECTO = United Kingdom → entityId = UK-UNITED-KINGDOM` 这条推导对殖民地、占领区、受托管理地都是错的。实测 1945 年：

| feature `id` | NAME | 当前 entityId | 语义上正确的「政权」 |
|---|---|---|---|
| 5 | Japan (USA) | `US-USA` | 日本（被美国占领） |
| 3 | Korea (USSR) | `RU-USSR` | 朝鲜（被苏联占领） |
| 218 | Korea (USA) | `US-USA` | 朝鲜（被美国占领） |
| 137 | Germany (Soviet) | `RU-USSR` | 德国（苏占区） |
| 143 | Germany (UK) | `UK-UNITED-KINGDOM` | 德国（英占区） |
| 144 | Germany (USA) | `US-USA` | 德国（美占区） |
| 145 | Germany (France) | `auto:france` | 德国（法占区） |
| 178 | United States | `US-USA` | 美国（本土，正确） |

**(P3) 40.4% 的 feature 没有身份。** 7,046 个 feature 的 `NAME` 与 `SUBJECTO` 同时为空，被合成到 `UNNAMED`。这个数字本身就是关系层「证据不足」的规模上限。

**本阶段的设计目标**：让上述三种情况**可以被表达**，而**不需要**改变 `entityId` 的既有语义、颜色分配机制或 54 个快照的任何字节。

## 3. Proposed Data Model

### 3.1 五层语义

```
第 0 层  upstream feature        上游 GeoJSON 的几何 + 属性（只读，永不修改）
第 1 层  evidence（证据）        NAME / SUBJECTO / PARTOF / ABBREVN / BORDERPRECISION / year
                                 + 派生证据 normalizedKey、cell（year,key,NAME）
第 2 层  identity（身份）        entityId —— 「这是哪个历史政权」        ← 颜色唯一来源
第 3 层  relation（关系）        sovereignId / authorityId / relationship  ← 本阶段新增
第 4 层  presentation（呈现）    color = f(entityId)；未来 P5 的详情面板读关系层
```

**分层硬规则**

| 编号 | 规则 |
|---|---|
| **A1** | `color` 只依赖 `entityId`。关系层三个字段**不是** `color` 的输入。 |
| **A2** | 关系层**不得**反向推导 identity：`sovereignId → entityId`、`authorityId → entityId`、`relationship → entityId` 全部禁止。 |
| **A3** | 关系层**可以**变化而 `entityId` 不变（Sierra Leone 的 colony → protectorate 不得拆出两个 polity）。 |
| **A4** | 第 2 层与第 3 层之间**没有函数依赖**：两层各自从第 1 层证据解析，互不调用（实现见 §5）。 |

### 3.2 与上一轮四层模型的差异

`reports/p4.1-sovereign-model-design.md` 的第一版把 sovereign 与实际控制者合为一层，已被用户判定不严谨。本设计的修正是：

- **拆成两个独立字段**：`sovereignId`（法理主权）与 `authorityId`（实际控制）。
- **补上 `relationship`** 作为第三个独立字段，用来表达 feature 所代表的 polity 与上述两者之间的政治关系。
- 明确 `authorityId ≠ sovereignId` 的常见情形：占领（`occupied`）、军事管理（`administered`）、托管（`trusteeship`）、委任统治（`mandate`）。

正确的表达示例（本设计的**目标语义**，具体历史值不在本阶段裁决）：

```
1945 Japan            → entityId = <日本 polity>   sovereignId = <日本 polity>   authorityId = <美国/SCAP>      relationship = occupied
1945 United States    → entityId = US-USA          sovereignId = US-USA          authorityId = US-USA           relationship = sovereign-territory
1945 Eritrea          → entityId = <厄立特里亚 polity> sovereignId = null          authorityId = <英国军管当局>    relationship = administered
```

## 4. Field Schema

### 4.1 feature 层记录（P4.1-A v1）

每个 feature 在关系层中对应一条记录，五个字段：

```jsonc
{
  "entityId":       "UK-UNITED-KINGDOM",   // string | null —— 由 identity resolver 产出，语义不变
  "sovereignId":    "UK-UNITED-KINGDOM",   // string | null —— 法理主权主体
  "authorityId":    "auth:UK",             // string | null —— 实际控制主体（独立命名空间）
  "relationship":   "colony",              // 11 值枚举，恒非空
  "resolutionStatus": "resolved"           // "resolved" | "unresolved"
}
```

机器可读 schema：`tests/fixtures/P4.1-A/relation-layer.schema.json`（JSON Schema 2020-12）。

### 4.2 规则层记录（authored，本阶段**不创建文件**）

关系层的值不是逐 feature 手写的，而是由**规则**在构建期解析出来的。配置文件放在**独立的关系层目录** `data/relations/`：

| 目录 | 唯一职责 | 内容 |
|---|---|---|
| `data/identity/` | `entityId` / `color` / identity resolver | `aliases.json`（手工实体与 `periods`）、`colors.json`（冻结颜色注册表） |
| `data/relations/` | `sovereignId` / `authorityId` / `relationship` | `relations.json`（关系规则）、`authorities.json`（authority 注册表，命名空间与形态已在 OQ-2 ✅ 冻结） |

**目录级隔离的理由**：identity 与 relation 是两层独立的解析过程（§3.1、§5.2）。若把 `relations.json` / `authorities.json` 放进 `data/identity/`，目录结构与职责说明会重新耦合，实施者容易顺手把关系规则写进 `aliases.json`，或在两侧共享解析状态。分目录后，「关系层不得反向推导 identity」（A2）这条硬规则在**文件系统层面**也有对应物：identity 工具不需要读 `data/relations/`，relation 工具不得写 `data/identity/`。

建议的规则文件为 `data/relations/relations.json`：

```jsonc
{
  "version": 1,
  "rules": [
    {
      "id": "UK-SL-COLONY",                      // 规则唯一 id，用于审计与冲突报错
      "match": {                                  // 选择器：全部字段可选，越具体优先级越高
        "key": "united kingdom",                  // 归一化后的 key
        "name": "sierra leone",                   // 归一化后的 NAME
        "years": [1808, 1960]                     // 闭区间，真实纪年
      },
      "output": {
        "sovereignId": "UK-UNITED-KINGDOM",
        "authorityId": "auth:UK",
        "relationship": "colony"                  // 1896 之后同一 polity 的 relationship 由更具体的规则覆盖
      },
      "source": "reports/p4.1-readonly-survey.md#4.2",   // 证据出处，必填
      "confidence": "medium"                              // high | medium | low，必填
    }
  ]
}
```

**关键约束**：规则的 `output` **不允许**出现 `entityId` 字段。规则文件里出现 `entityId` 即为构建错误 —— 这把 A2 从「约定」变成「机器可检查的约束」。

### 4.3 字段分类（P4.1 必需 vs 未来扩展）

| 字段 | 层 | 分类 | 说明 |
|---|---|---|---|
| `entityId` | feature | **P4.1 必需**（已存在） | 语义与取值完全不变 |
| `sovereignId` | feature | **P4.1 必需** | 可为 `null` |
| `authorityId` | feature | **P4.1 必需** | 可为 `null`；独立命名空间 |
| `relationship` | feature | **P4.1 必需** | 恒非空，11 值枚举 |
| `resolutionStatus` | feature | **P4.1 必需** | 2 值，构建期派生 |
| `match` / `output` / `source` / `confidence` / `id` | 规则 | **P4.1 必需** | 审计与冲突判定所需 |
| `validFrom` / `validTo`（feature 层） | feature | **未来扩展（不落地）** | 见下 |
| `fieldStatus`（逐字段状态对象） | feature | **未来扩展（不落地）** | 见 §6.5 |
| `confidence` / `notes`（feature 层） | feature | **未来扩展（不落地）** | 置信度属于规则，不属于 feature |
| `evidenceRef`（feature 层回指规则 id） | feature | **未来扩展（不落地）** | 审计便利，必要时再加 |

**关于 `validFrom` / `validTo` 的结论：P4.1 不需要。**
理由：时间已经由「规则 `match.years` + 该年份的快照」这一对确定，且 `aliases.json` 的 `periods` 已承担 polity 的纪年区间职责。再引入 feature 级的 validFrom/validTo 会产生**第二个时间真相来源**，与 `periods` 冲突。若将来需要在快照之间表达亚年级精度（例如 1960-07-01 独立），应先裁定它与 `periods` 的关系，届时作为独立提案。

### 4.4 `null` 的定义与 `sovereignId = null` 的双重语义

`null` 唯一允许的含义：

```
null  ==  「证据不足，无法确定」  或  「该字段对这一 feature 不适用」
```

禁止：

- ❌ `sovereignId: "unknown"`、`authorityId: "unknown"` —— 不得制造假实体占位。
- ❌ 用 `"N/A"` / `"-"` / `""` 表示未知。
- ❌ 为了让字段看起来完整而填入「最接近」的 id。

需要表达「关系未知」时，唯一正确写法是 `relationship: "unknown"`。

#### 4.4.1 `sovereignId = null` 本身不足以区分两种情形

`sovereignId` 为 `null` 时，历史上可能是两种**完全不同**的情况，而**单看这个字段无法区分**：

| 情形 | 含义 | 我们掌握的知识 |
|---|---|---|
| **A. 证据不足** | 无法确定法理主权主体 | 我们**不知道**主权者是谁 |
| **B. 已确认不存在单一法理主权主体** | 历史上**确定**不存在一个可由当前 schema 表示的单一法理主权者（军管地、共同占领下的全境、无单一主权者的过渡状态等） | 我们**知道它没有** |

**不新增字段、不引入第三态、不新增枚举。** 两种情形由 `relationship` + `resolutionStatus` + 规则 `source` 三者共同区分：

```jsonc
// 情形 A：证据不足（→ 进入 unresolved 工作队列）
{ "sovereignId": null, "authorityId": null, "relationship": "unknown",
  "resolutionStatus": "unresolved" }

// 情形 B：已确认无单一法理主权者（→ 已由规则断言，可审计）
{ "sovereignId": null, "authorityId": "auth:US", "relationship": "occupied",
  "resolutionStatus": "resolved" }
```

判定式（可机器检查）：

```
情形 A  ⟺  sovereignId = null  且  relationship = "unknown"  且  resolutionStatus = "unresolved"
情形 B  ⟺  sovereignId = null  且  relationship ∈ 11 值中除 unknown 以外的某个明确值
                                且  resolutionStatus = "resolved"（必须命中一条规则）
```

推论（实施期硬约束，与 `tests/fixtures/P4.1-A/relation-layer.schema.json` 的一致性规则一致）：

1. 任何 `relationship ≠ "unknown"` 的记录，其 `resolutionStatus` 必须是 `resolved`，且必须能回溯到一条规则（规则 id + `source` + `confidence`）。
2. 任何 `resolutionStatus = "unresolved"` 的记录，必须是 `null + null + unknown` 形状。
3. 因此「情形 B」永远留有审计线索：是哪条规则、依据什么 `source`、以什么 `confidence` 断言了「无单一主权者」。禁止把情形 B 写成 `unknown` 来偷懒 —— 那会把一个**已确认的历史事实**降级成未知。

> 边界说明：`authorityId = null` **没有**对应的双语义问题，它一律表示「无（或未知）实际控制主体」；只有 `sovereignId` 的 `null` 需要上述三段式消歧。

### 4.5 命名空间

| 字段 | 允许取值 | 是否要求解析到既有实体 |
|---|---|---|
| `entityId` | 既有实体的 id，或哨兵 `UNNAMED`（见 §6.6） | 是（`UNNAMED` 除外） |
| `sovereignId` | 既有 polity 实体 id，或 `null`（**命名空间已冻结**，见 §13 OQ-1 ✅；不使用独立 `sov:` 命名空间） | **是** —— 法理主权在模型中总是一个 polity，可直接通过 `entities.json` 审计 |
| `authorityId` | `auth:<SLUG>`，或 `null`（**命名空间已冻结**，见 §13 OQ-2 ✅） | 否 —— 独立命名空间，指向 `data/relations/authorities.json` 中的注册项 |
| `relationship` | §7 的 11 项 | — |

`authorityId` 用 `auth:` 前缀是**结构性护栏**（**命名空间已冻结**，见 §13 OQ-2 ✅）：占领当局、军事管理当局、多国管制机构**不是** polity，绝不能被写进 polity 命名空间，也就永远不会与 `entityId` 混淆。已冻结设计（**本阶段不创建**）的配套注册表是 `data/relations/authorities.json` —— 它属于**关系层目录**（与 `relations.json` 平级），**不在 `data/identity/` 下**：

```jsonc
{
  "version": 1,
  "authorities": {
    "auth:SCAP":  { "label": "盟军总司令部", "labelEn": "Supreme Commander for the Allied Powers", "controllerEntityId": "US-USA", "note": "controllerEntityId 仅为说明性元数据，不参与 entityId 解析" },
    "auth:UK":    { "label": "英国", "labelEn": "United Kingdom", "controllerEntityId": "UK-UNITED-KINGDOM" },
    "auth:UK-BMA":{ "label": "英国军事管理当局", "labelEn": "British Military Administration", "controllerEntityId": "UK-UNITED-KINGDOM" }
  }
}
```

> `controllerEntityId` 是**单向说明性元数据**（authority → polity），它使审计员能看出「谁在管」，但**不得参与 identity resolver 或颜色分配**：代码中**不存在**从它推导 polity、`entityId` 或颜色的路径。该注册表与 `auth:<SLUG>` 命名空间**已在 OQ-2 冻结采纳**（✅）：registry 文件为 `data/relations/authorities.json`（本阶段不创建）。

### 4.6 存储形态：两个方案与推荐（**OQ-10 尚未批准，本阶段不实施**）

| | 方案 A：写进 `properties` | **方案 B：sidecar（推荐，待 OQ-10 批准）** |
|---|---|---|
| 形态 | 每个 feature 的 `properties` 增加 4 个键 | 新增 `public/data/relations/<year>.json`，按 feature `id` 关联 |
| 54 个年份文件 | **被修改**（体积 +约 0.4 MB） | **字节级不变** |
| 与现有校验的关系 | 会改变 `entities.json`/颜色以外的产物哈希 | 现有 56 个产物哈希完全不动 |
| 前端读取 | 一次 fetch | 多一次 fetch（可按年按需加载，与 `loadYear` 的 LRU 同构） |
| 回滚 | 重新生成年份文件 | 删除 `relations/` 目录即可 |
| 本阶段推荐 | 否 | **是**（仅为推荐；**OQ-10 未批准前不得实施**） |

> **边界（冻结）**：sidecar 目前只是推荐方案，**不得在 P4.1-A 阶段实施** —— 不创建 `data/relations/**`，不创建 `public/data/relations/**`，不生成 54 个 relations 年份文件，不修改 `manifest.json`，不修改任何生产数据。OQ-10 保持 OPEN QUESTION，待正式进入 P4.1-B 前单独批准。

**推荐理由（可验证）**：方案 B 让「关系层不影响身份与颜色」成为**可机械证明的事实** —— 关系层产物是新增文件，54 个年份文件的 SHA-256 必然不变；而方案 A 必须靠哈希比对是否「除新增键外无差异」来间接论证。

`relations/<year>.json` 草案：

```jsonc
{
  "year": 1945,
  "file": "years/world_1945.json",
  "relations": {
    "5":   { "entityId": "JP-…", "sovereignId": "JP-…", "authorityId": "auth:SCAP", "relationship": "occupied", "resolutionStatus": "resolved" },
    "178": { "entityId": "US-USA", "sovereignId": "US-USA", "authorityId": "auth:US", "relationship": "sovereign-territory", "resolutionStatus": "resolved" }
  }
}
```

`relations` 的键是年份文件内 feature 的 `id`。**该关联方式已被验证可靠**：54/54 文件的 `id` 在文件内唯一且连续（`reports/p4.1-readonly-survey.md` §2.4）。注意 `id` **不是**跨年份稳定标识（全局仅 1,942 个不同值），因此 sidecar 必须按年存放、按年读取 —— 这正是现有 `loadYear(year)` 的形状。

## 5. Resolver Architecture

### 5.1 数据流

```
                        ┌──────────────────────────── raw feature (只读) ────────────────────────────┐
                        │  geometry（关系层绝不读取）                                                  │
                        │  properties: NAME / SUBJECTO / PARTOF / ABBREVN / BORDERPRECISION          │
                        │  year（来自快照名）                                                        │
                        └───────────────────────────────────┬──────────────────────────────────────┘
                                                            ▼
                                          ┌──────────── 证据层 evidence ────────────┐
                                          │  rawKey     = SUBJECTO || NAME          │   （沿用现有规则，不改）
                                          │  normalizedKey = normalizeKey(rawKey)   │   （复用同一函数，保证口径一致）
                                          │  name / subject / partOf / abbrev       │   （逐字段归一化 + 空白折叠）
                                          │  cell = (year, normalizedKey, name)     │
                                          └───────┬───────────────┬─────────────┬───┘
                                                  │               │             │
        ┌─────────────────────────────────────────┘               │             └───────────────────────────┐
        ▼                                                         ▼                                         ▼
┌──────────────────────┐                          ┌──────────────────────────┐            ┌──────────────────────────────┐
│ ① entity resolver    │                          │ ② sovereign resolver     │            │ ③ authority resolver         │
│  (既有实现，不改)     │                          │   独立规则表              │            │   独立规则表                  │
│  key 派生 → 归一化    │                          │   match(cell) → id|null  │            │   match(cell) → auth:*|null   │
│  → 空档切分 → 手工    │                          └────────────┬─────────────┘            └───────────────┬──────────────┘
│  认领 → color        │                                       │                                          │
└──────────┬───────────┘                                       │                                          │
           │                                                   │                                          │
           │                            ┌──────────────────────┴───────────────┐                          │
           │                            ▼                                      ▼                          │
           │                ┌──────────────────────────┐          ┌──────────────────────────────┐        │
           │                │ ④ relationship resolver  │          │ ⑤ resolutionStatus 派生       │◀───────┘

           │                                                                     │
           ▼                                                                     ▼
   properties.entityId / properties.color                       public/data/relations/<year>.json
   （形状与取值完全不变）                                          （新增产物，不进颜色链路）
```

### 5.2 共享与禁止（明确矩阵）

| | entity resolver | sovereign resolver | authority resolver | relationship resolver |
|---|---|---|---|---|
| **共享输入：证据层 `cell` + 归一化结果** | ✅ | ✅ | ✅ | ✅ |
| **共享输入：年份 / 快照索引** | ✅ | ✅ | ✅ | ✅ |
| 读取 `entity resolver` 的输出（`entityId`） | — | ❌ **禁止** | ❌ **禁止** | ❌ **禁止** |
| 读取 `sovereign resolver` 的输出 | ❌ **禁止** | — | ❌ **禁止** | ❌ **禁止** |
| 读取 `authority resolver` 的输出 | ❌ **禁止** | ❌ **禁止** | — | ❌ **禁止** |
| 读取 `relationship resolver` 的输出 | ❌ **禁止** | ❌ **禁止** | ❌ **禁止** | — |
| 读取 geometry | ❌ **禁止** | ❌ **禁止** | ❌ **禁止** | ❌ **禁止** |
| 读取 `BORDERPRECISION` | ✅（现有行为） | ❌ | ❌ | ❌ |

**为什么连「关系层读 entityId」也禁止**：一旦允许，就会自然演化出「只在某 entityId 下改关系」的写法，随后演化为「关系变了所以换 entityId」的反向依赖（正是 A2 禁止的）。把 `entityId` 从关系 resolver 的输入中彻底移除，可以让 A2 具备**静态可检查性**（resolver 签名里没有 `entityId` 参数）。代价是规则必须写得更具体（用 `key` + `name` + `years` 而不是 `entityId`），这是可接受的、也更可审计的代价。

### 5.3 匹配优先级与选择器

`match` 支持三个可选取字段：`key`（归一化后的 raw key）、`name`（归一化后的 NAME）、`years`（闭区间，真实纪年）。

```
优先级（从高到低，取第一个命中；同级多规则命中且输出不同 = 构建失败）：
  1. key + name + years
  2. key + name
  3. key + years
  4. key
  5. name + years
  6. name
  7. 无匹配  →  sovereignId = null, authorityId = null, relationship = "unknown", resolutionStatus = "unresolved"
```

- **不使用 geometry、不使用邻国、不使用年份插值。**
- `name` 的比较对象是**归一化后**的 NAME；空白/空串 NAME 归一化为 `null`，并作为一个合法选择器值（实测这类 feature 共 12 个：`-5000:1`、`-2000:1`、`100:1`、`700:1`、`1783:1`、`1815:7`，例如 `1815 dutch east indies` 的 7 个 feature、`cardial ware culture` 的整空白 NAME）。
- 本阶段**不提供** feature 级选择器（如按 `id` 定位）。理由：实测 241 个「同一 `(year, key, NAME)`」重复组中，**组内出现多个不同 entityId 的组数 = 0**，即现有证据粒度足以唯一确定语义；若将来出现「同证据、不同关系」的组，应作为**新的表达能力缺口上报**，而不是引入一个可以偷偷夹带身份判断的后门选择器（见 **OQ-11**）。

### 5.4 覆盖度审计（关系层的必交产物）

构建期必须产出（P4.1-B 实施时）：

1. 每个 `(year, key, name)` 证据单元是否被某条规则命中 → **证据单元总数 10,095**（其中 9,713 个是 `(year, key)` 单元）。
2. 关系规则**未覆盖**的证据单元清单（工作队列）。
3. 关系规则覆盖不到的 feature 数：至少 **7,046**（无 key）+ 12（有 key 无 NAME）= **7,058 = 40.5%**，必然落在 `unresolved`。
4. 规则冲突清单（同格多输出）。
5. 建议产物：`reports/p4.1-B-relation-coverage.md`（本阶段不生成）。

> 实测规模参考：383 个 feature 的 NAME 带括号限定词且分布 **249 种**（`UK`×27、`France`×13、`Spain`×11、`GB`×8、`Portugal`×7、`Dutch`×5、`Belgium`×5、`USA`×3、`IT`×2、`Italy`×2、`Indian princely state`×4、`Oklahoma`×28 …）。这些正是关系层的**第一批必填目标**，也是「一个 raw key 混装」的最直接证据。

## 6. Null / Unknown / Unresolved Semantics

### 6.1 三态定义

| 情形 | `sovereignId` | `authorityId` | `relationship` | `resolutionStatus` |
|---|---|---|---|---|
| **有证据** | id，或 `null` = **情形 B**（规则显式声明「无单一主权者」，见 §6.2） | id 或 `null` | 具体枚举值（≠ `unknown`） | `resolved` |
| **证据不足** | `null` = **情形 A**（见 §6.2） | `null` | `unknown` | `unresolved` |
| **证据冲突** | `null` | `null` | `unknown` | `unresolved` + 记入冲突清单 |
| **不适用**（如无 key 的 `UNNAMED`） | `null` | `null` | `unknown` | `unresolved` |

### 6.2 `sovereignId = null` 的双重语义（§4.4.1 的展开）

`null` 在 `sovereignId` 上是**多义的**：它既可能表示「不知道」，也可能表示「知道它没有」。本设计**不新增字段**来编码这个差别，而是要求用 `relationship` + `resolutionStatus` + 规则 `source` 三段式消歧：

| | **情形 A：证据不足** | **情形 B：已确认无单一法理主权者** |
|---|---|---|
| `sovereignId` | `null` | `null` |
| `authorityId` | `null` | 通常有值（如 `auth:US`、`auth:UK-BMA`），也可为 `null` |
| `relationship` | `unknown` | 11 值中除 `unknown` 之外的某个明确值 |
| `resolutionStatus` | `unresolved` | `resolved`（必须命中规则） |
| 审计线索 | 无（记入 unresolved 工作队列） | 规则的 `source` + `confidence` 必须写明「为何不存在单一主权者」 |
| 本项目中的候选例子（**未裁决**） | 1800/1815 双声索的 `Kuril Islands`（raw key `(russian and japanese claim)`，id=610/368）：单值无法表达两个声索方，按证据冲突处理、形状归入 A（见 OQ-8） | 1945 年德国四占领区（上游已是 4 个独立 feature，各自 authority 不同）、1941–1952 厄立特里亚军管（`auth:UK-BMA`，见 §9.4，**本阶段不裁决**） |

三类禁止：

```
❌ 不新增 sovereigntyStatus / 第三态 / 任何新字段来表达 A 与 B 的差别
❌ 不新增、不改名、不重定义任何 relationship 枚举值
❌ 不因为 sovereignId = null 就把 relationship 自动降级为 unknown
❌ 也不为了消灭 null 而给情形 B 编造一个假的主权者 id
```

### 6.3 两类冲突必须分开处理

| 类型 | 例子 | 处理方式 |
|---|---|---|
| **规则冲突**（配置缺陷） | 两条同优先级规则对同一证据单元给出不同输出 | **构建直接失败**，报出规则 id 与证据单元（沿用 `scripts/lib/identity.mjs:169-171` 的既有惯例：`throw new Error(...)`） |
| **证据冲突**（史实/数据分歧） | 上游把厄立特里亚 1945 年放在 `United Kingdom` key 下；`PARTOF` 写成 `Khoiasan`（拼写错误）；`(Russian and Japanese claim)` 一个 feature 两个声索方 | **不裁决**：`relationship = "unknown"`、`resolutionStatus = "unresolved"`，记入冲突清单，升级为 OPEN QUESTION |

### 6.4 绝对禁止（写进设计，成为实施期硬约束）

```
❌ 冲突 → AI 猜测
❌ 证据不足 → 用「最接近」的枚举值填充
❌ 用 geometry / 邻国 / 年份 / 常识 推断 polity 或关系
❌ 为了让字段非空而拆 polity、改 entityId、改颜色
```

### 6.5 `resolutionStatus` 的定义与第三种状态

`resolutionStatus` 是**派生字段**，是四个字段的确定性函数：

```
resolutionStatus = "resolved"   当且仅当 该 feature 的 (year,key,name) 命中了一条规则
                                          （规则可以显式断言 relationship="unknown"，这也算 resolved）
                 = "unresolved" 否则
```

- 第一版**只有 2 个值**，与用户给出的候选一致。
- **设计建议（本阶段不落地）**：标量 `resolutionStatus` 无法表达「哪个字段未知」。若将来需要，建议增加**逐字段**状态对象 `fieldStatus: { sovereign: "resolved"|"unresolved", authority: ..., relationship: ... }`，并保留标量作为其聚合结果。这属于 **OQ-12**，本阶段不写入 schema。

### 6.6 UNNAMED 处理（本阶段保持保守）

- `UNNAMED` **不是**历史政权，**保持**它现有的哨兵身份：不进 `entities.json`、不进颜色注册表、颜色恒为 `UNNAMED_COLOR`。
- 关系层对这类 feature 的记录固定为：`entityId: "UNNAMED"`、`sovereignId: null`、`authorityId: null`、`relationship: "unknown"`、`resolutionStatus: "unresolved"`。
- **不猜测**、**不因为邻接关系给出估计值**、**不生成任何「推测 polity」**。
- 「哨兵 `UNNAMED`」与「`entityId: null` + `resolutionStatus: unresolved`」两种表达是否要统一，是 **OQ-9**，本阶段不动生产数据。

## 7. Relationship Enum

### 7.1 冻结枚举（11 项，本阶段不增删改）

| 值 | 本设计给出的判定语义（**不是**历史赋值） | `sovereignId` 预期 | `authorityId` 预期 |
|---|---|---|---|
| `sovereign-territory` | polity 自身就是主权者、且实际由自身治理的本土 | 非空（= 自身或所属主权 polity） | 非空（通常 = `sovereignId`） |
| `colony` | 由外部主权者直接统治、无本地自主法统的领地 | 非空（宗主） | 非空（宗主行政机构） |
| `protectorate` | 保留本地统治者、对外关系与防务由外部主权者控制 | 非空（保护国） | 非空 |
| `occupied` | 主权仍在原 polity，但领土被他方军事占领 | 非空（原主权者） | 非空（占领方），**且 ≠ `sovereignId`** |
| `dependency` | 从属领地（非殖民地、非保护国的从属形态） | 非空 | 非空 |
| `mandate` | 国际联盟委任统治 | 非空（委任方） | 非空 |
| `trusteeship` | 联合国托管理事会体系下的托管 | 非空（托管方） | 非空 |
| `autonomous` | 在某一主权者之下的自治单元 | 非空 | 非空或 `null` |
| `condominium` | 两国或多国共同行使主权 | 非空（若可归为单一主体则写之，否则 `null`） | 非空 |
| `administered` | 由他方（军管当局、临时行政当局）实施行政管理 | 非空或 `null` | 非空，**通常 ≠ `sovereignId`** |
| `unknown` | 证据不足 / 证据冲突 / 不适用 | `null` | `null` |

### 7.2 单值约束（第一版）

`relationship` **必须**单值。若一个历史案例同时具有多种性质（例如「1896 年前的海岸殖民地 + 腹地保护地」）：

- 若证据能区分（不同 feature / 不同地区 / 不同时期）→ 用**不同规则**分别赋单值。
- 若证据**不能**区分（同一个 feature 同时是 A 又是 B）→ **上报 schema 表达能力不足**，记为 OPEN QUESTION，**不得**：
  - 创造 `colony+protectorate` 之类的复合枚举；
  - 拆 entity；
  - 改 `entityId`；
  - 改颜色。

### 7.3 已知表达缺口（全部进 §13，本阶段不自选近似值）

| 缺口 | 证据（54 个快照内实测） | 为什么现有枚举不够 |
|---|---|---|

## 8. Cross-key Handling（架构测试）

### 8.1 核心规则

> **raw key 只是 identity resolver 的输入证据之一，不是 historical polity identity 本身。**

```
❌  SUBJECTO = United Kingdom  →  entityId = UK-UNITED-KINGDOM
❌  raw key  = USA             →  entityId = US-USA
❌  raw key  = USSR            →  entityId = RU-USSR
```

正确的关系：identity resolver 依据「归一化 key + 时间连续性 + 手工认领」决定 polity；关系 resolver 依据「证据单元」独立决定 sovereign / authority / relationship。**两者都读同一份证据，但不互相调用**（§5.2）。

### 8.2 UK（6 个 raw key 混装 母国 / 殖民地 / 占领区 / 属地）

| raw key | 年份（实测） | 内容性质 | 当前结果 |
|---|---|---|---|
| `uk` | 1783(f=3), 1800(f=6) | 母国自身 + 殖民地（`British Guiana`）+ 君合国（`Hanover`、`Kingdom of Ireland`）+ 无法解释（`Mecklenburg-Strelitz`） | `UK-UNITED-KINGDOM` |
| `united kingdom` | 1715(f=9), 1815, 1878, 1880, 1900, 1914, 1920, 1930, 1938(f=20), 1945(f=25), 1960, 1994, 2000, 2010 | 母国 + 殖民地 + 占领区 + 属地 | `UK-UNITED-KINGDOM`（全部同年同色） |
| `united kingdom of great britain and ireland` | 1815, 1878, 1880, 1900(f=7), 1914(f=12), 1920(f=9), 1930(f=9), 1938(f=5) | **与上一行同年并存**：1900 年是澳大利亚各州，1914/1920 是非洲与中东属地 | `UK-UNITED-KINGDOM`（用户已裁定同一政权） |
| `great britain` | 1878, 1880 | NAME = `Gold Coast (GB)` —— 只是「英国属」的归类标签 | `auto:great britain`（**不得**凭字符串归入 UK） |
| `england` | 1000–1500（本体） / 1650,1700（NAME = `Virginia`、`Massachusetts Bay`） | 后两个是殖民地 | `auto:england` / `auto:england#1` / `auto:england#2` |
| `england and ireland` | 1530, 1600, 1650, 1700 | 1707 年前的英格兰王国 + 爱尔兰 | `auto:england and ireland`（独立政权，非 UK） |

**新模型如何表达**（示意，历史值待裁决）：

```
1945 id=4   NAME=United Kingdom        → relationship = sovereign-territory  (authority = auth:UK)
1945 id=27  NAME=Sierra Leone          → relationship = colony               (sovereign = UK-UNITED-KINGDOM, authority = auth:UK)
1945 id=48  NAME=Swaziland             → relationship = protectorate         (sovereign = UK-UNITED-KINGDOM)
1945 id=113 NAME=Eritrea               → relationship = administered         (sovereign = null, authority = auth:UK-BMA)
1945 id=226 NAME=Hong Kong             → relationship = colony / dependency  （PARTOF = null，需人工裁定，见 OQ）
1945 id=143 NAME=Germany (UK)          → relationship = occupied             (sovereign = <德国 polity>, authority = auth:UK)
1878/1880   NAME=Gold Coast (GB)       → relationship = colony               (sovereign = UK-UNITED-KINGDOM)
```

**效果**：`UK-UNITED-KINGDOM` 的 entityId 边界与颜色**完全不动**，而「本土 / 殖民地 / 占领区 / 属地」在关系层被区分开。这正是「关系可变化、身份不变」（A3）的构造成果。

### 8.3 USA（3 个 raw key + 占领与属地）

| raw key | 年份 | 实测内容 |
|---|---|---|
| `united states of america` | 1783, 1800, 1878, 1880, 1900 | 全部 f=1（本体） |
| `united states` | 1815(1), 1914, 1920, 1930, 1938(f=3: Philippines / US / Guam), 1945(f=1: 本体 id=178), 1960, 1994, 2000, 2010 | 本体 + 属地 |
| `usa` | 1945(f=5) | `Japan (USA)` id=5、`Germany (USA)` id=144、`United States Virgin Islands` id=158、`United States` id=178、`Korea (USA)` id=218 |

**新模型**：`US-USA` 仍只表示美国 polity；`Japan (USA)` 的 entityId 必须是**日本 polity**（不是 `US-USA`），`authorityId = auth:US`（或 `auth:SCAP`）、`relationship = occupied`。实测已确认四国占领区在上游是**4 个独立 feature**，因此单值 `authorityId` 足够。

### 8.4 USSR（RSFSR / USSR 与占领区）

`key = ussr` 出现在 1920, 1930, 1938, 1945, 1960：

- 1920 年 4 个 feature（`Georgia`/`Armenia`/`Azerbaijan`/`USSR`）→ 已由 `RU-RSFSR`（`periods [[1917,1922]]`）认领。
- 1930+ → `RU-USSR`。
- 1945 年 `Korea (USSR)` id=3 与 `Germany (Soviet)` id=137 当前都是 `RU-USSR`；新模型中它们是**朝鲜**与**德国**的 polity，`authorityId = auth:USSR`、`relationship = occupied`。

**注意**：`RU-RSFSR` / `RU-USSR` 的拆分与 `periods` 是**已冻结的历史裁决**，本阶段不改动、不重裁。

### 8.5 Denmark-Norway / Sweden-Norway

| raw key | 年份（实测） | 当前实体 | 设计要点 |
|---|---|---|---|
| `denmark` | 1100–1300 / 1815–2010 | `auto:denmark` / `auto:denmark#1` | 1513 段空档由 `denmark-norway` 覆盖 |
| `denmark-norway` | 1000（`SUBJECTO` 为空）/ 1492–1800 | `auto:denmark-norway` / `DK-NORWAY` | 1000 年落在 `DK-NORWAY` 的 `[[1397,1814]]` 之外 → 仍是 auto |
| `sweden-norway` | 1815（`SUBJECTO` 为空）/ 1878, 1880, 1900 | `SE-NORWAY` | 上游用 en dash `Sweden–Norway` |
| `norway` | 1100–1300 / 1914–2010 | `auto:norway` / `auto:norway#1` | — |

**设计要点**：双元王国**已经**是独立 polity（用户已裁定），因此它们的关系层应为 `sovereign-territory`（自身即主权者），而**不是**把挪威写成丹麦的 `colony`。这验证了 A2/A3：polity 边界由 identity 层决定，关系层不得反向改写它。

### 8.6 Japan / Italy

- Japan：`Japan (USA)` 1945 → polity = 日本、`authority = auth:SCAP`、`relationship = occupied`（不得变成 `US-USA`）。
- Italy：1938 年 `Eritrea (Italy)`、`Ethiopia (Italy)`、`Italian Somaliland` 与 `Italy` 同在 `italy` key 下（f=5）；1914 年为 `Kingdom of Italy` + `Eritrea`/`Libya`/`Italian Somaliland`（f=4）。新模型下 `Eritrea (Italy)` 的 polity 是**厄立特里亚**、`sovereign = IT-…`（意属殖民地时期）、`relationship = colony`；而 `Italy` 本体是 `sovereign-territory`。

### 8.7 为什么该设计能同时满足两条看似冲突的要求

| 要求 | 满足方式 |
|---|---|
| 同一政权跨年份同色（含 `United Kingdom` / `United Kingdom of Great Britain and Ireland` / `UK` 归并） | 由 **identity 层**的 `keys` + `periods` 表达（已实现），关系层不参与 |
| 不把 Jamaica / Sierra Leone / Tanganyika / Northern Rhodesia / Nyasaland … 并入英国 | 由 **关系层**分别赋 `colony`/`protectorate`/`mandate`/`administered`，`authorityId` 指向英国，而 `entityId` 保持不变（当前为 `UK-UNITED-KINGDOM`） |
| 占领不改变被占领国的政权身份 | `relationship = occupied` + `authorityId ≠ sovereignId`；`entityId` 仍是被占领国 |
| 将来把殖民地「归还」给各自 polity（Step B） | 这是 **identity 层**的独立决策，与关系层解耦：可以在不改关系层的前提下做，也可以只做关系层而不动 entityId |

### OQ-1 `sovereignId` 的命名空间 —— ✅ **已裁定（冻结）**
1. **案例**：1945 厄立特里亚（英国军管）、1945 日本（美国占领）、1945 德国（四国占领）。
2. **缺口（已解）**：`sovereignId` 若采用 polity 命名空间，则「无单一法理主权者」的情形只能用 `null` 表达，无法记录声索方（后者另见 OQ-8 的多主体问题）；若采用独立命名空间，则会与 `entityId` 产生概念重叠。
3. **裁定（用户 m02288，v3 正式冻结）**：**`sovereignId = 既有 polity entityId | null`**。**不使用独立 `sov:` 命名空间。**
4. **理由（用户给出）**：①sovereign 的语义主体仍然是历史 polity；②可直接通过 `entities.json` 审计（T14 可断言「`sovereignId` 必须存在于 `entities.json`」）；③与 `entityId` 保持同一 polity 命名空间。
5. **硬约束**：`sovereignId` **不得反向参与 entityId resolver 或 color resolver**（见 A2）。此条已裁定，不再是待决问题。

### OQ-2 `authorityId` 命名空间与 authority 注册表 —— ✅ **已裁定（冻结）**
1. **案例**：`auth:SCAP`、`auth:UK-BMA`、`auth:US`、`auth:USSR`、`auth:ALLIED-CONTROL-COUNCIL`。
2. **缺口（已解）**：占领方/军管当局**不是** polity，若直接写 `authorityId = "US-USA"` 就会重新引入「控制者 = 政权」的混淆。
3. **裁定（用户 m02288，v3 正式冻结）**：**`authorityId = auth:<SLUG> | null`**；authority 注册表正式设计为 **`data/relations/authorities.json`**（关系层目录，与 `relations.json` 平级，**不在 `data/identity/` 下**；本阶段不创建）。
4. **硬约束**：注册表中的 `controllerEntityId` **仅作为 authority → polity 的说明性元数据，不得参与 identity resolver 或颜色分配**。
5. **可机器校验**：T14 断言 `authorityId` 匹配 `^auth:[A-Z0-9][A-Z0-9-]*$` 或为 `null`。此条已裁定，不再是待决问题。

### OQ-11 是否需要 feature 级选择器（`featureId`）作为最后手段
1. **案例**：实测 241 个「同一 `(year, key, NAME)`」重复组中，**组内出现多个 entityId 的组数 = 0**；但 364 个 `(year, key)` 重复组（覆盖 8,035 个 feature）说明「多 feature 共享部分证据」是常态。
2. **缺口**：若将来出现「同证据单元、需要不同关系」的情况，当前选择器无法表达。
3. **候选**：(a) 不提供 feature 级选择器，遇到即报 OPEN QUESTION（本设计采用）；(b) 允许按 feature `id` 定位（有夹带身份判断的风险，且 `id` 仅文件内唯一）。
4. **推荐**：(a)。理由：把表达能力缺口暴露出来，比引入一个可以绕过 A2 的后门更安全。

### OQ-12 `resolutionStatus` 是否需要第三态 / 逐字段状态
1. **案例**：仅 `sovereignId` 未知、但 `relationship` 已知（或反之）的 feature。
2. **缺口**：标量状态无法表达「哪个字段未知」。
3. **候选**：(a) 保持 2 值标量（本设计采用）；(b) 增加 `partial` 第三态；(c) 增加逐字段 `fieldStatus` 对象（标量作为聚合）。
4. **推荐**：(c) 作为未来扩展，(a) 作为第一版。理由：`partial` 与 `fieldStatus` 相比信息量更低且会引入第三种「半已知」语义。
5. **为何不自裁**：你要求「如认为需要第三种状态，请列为设计建议，不要自行落地」。

### OQ-13 `validFrom` / `validTo` 与「无快照区间」
1. **案例**：Eritrea 1962–1993 **没有任何快照**（1960 与 1994 相邻）；Tanzania 1961/1963、Zimbabwe 1923/1953/1965 同样落在快照之间。
2. **缺口**：关系层以 (year, key) 为单位，无法为「无快照的年份区间」建立记录；而历史边界常落在这些区间内。
3. **候选**：(a) 不表达（本设计采用：关系层只覆盖快照覆盖的年份）；(b) 引入 feature 级 `validFrom`/`validTo`；(c) 引入独立的「时间线事件」表（P5 历史事件层的雏形）。
4. **推荐**：(a) 第一版；(c) 作为 P5 的候选承载方式。理由：给关系层加时间区间会制造第二个时间真相来源，与 `periods` 冲突。
5. **为何不自裁**：这会决定历史边界信息最终存在哪里，影响 P5 的架构。

### OQ-14 变更门禁方式（git vs 哈希）
